# Technical SEO implementation spec — 2026

Status: PREPARED ONLY — DO NOT DEPLOY
Branch: `seo-2026-content-pack`

This file defines the technical implementation required once the production source code is present in this repository.

## 1. Canonical URL rules

- Define one production host and use HTTPS everywhere.
- Every indexable SEO page must output exactly one self-referencing canonical URL.
- Canonical URLs must be present in the initial HTML when possible.
- Do not output conflicting canonicals between server-rendered HTML and client-side JavaScript.
- Do not canonicalize all SEO pages to the homepage.
- Query-string variants generated by tracking parameters must not become independent canonical pages.
- Include only canonical indexable URLs in the sitemap.

Example:

```html
<link rel="canonical" href="https://YOUR-PRODUCTION-DOMAIN/google-drive-link-checker" />
```

## 2. Robots rules

Production target:

```txt
User-agent: *
Allow: /

Sitemap: https://YOUR-PRODUCTION-DOMAIN/sitemap.xml
```

Do not use `robots.txt` as a substitute for `noindex`. A blocked URL can still appear in search results without a snippet if Google discovers it elsewhere.

Preview and staging deployments should remain non-indexable through platform-level protection and/or `noindex` controls. Do not accidentally ship preview-only noindex directives to production.

## 3. XML sitemap

Generate `/sitemap.xml` from the site's route source of truth rather than maintaining duplicate URL lists manually once the application is implemented.

Include:

- homepage
- core checker pages already intended for organic search
- all 10 priority routes in `SEO_ROUTE_MANIFEST.json`
- future useful indexable pages only after they contain substantive unique content

Exclude:

- API routes
- result URLs containing user-submitted link data
- temporary/share-result IDs unless a deliberate public-indexing product exists
- authentication pages
- redirects
- 404/soft-404 pages
- duplicate parameter variants
- preview/staging URLs

Use absolute canonical URLs. Do not add fake `lastmod` timestamps on every build. Set `lastmod` only when it reflects a meaningful content or structured-data update.

Do not waste effort on `<priority>` or `<changefreq>` for Google; Google ignores those values.

## 4. Metadata

Every indexable page needs:

- unique `<title>`
- unique meta description
- one clear visible H1
- self canonical
- Open Graph title/description where sharing matters
- stable favicon

Google may rewrite title links or snippets. Metadata should therefore accurately summarize the visible page rather than attempt keyword stuffing.

## 5. Page rendering and crawlability

Critical explanatory copy must be rendered as crawlable HTML and not exist only after a user submits a URL to the checker.

SEO landing pages must return HTTP 200 when valid and must not require JavaScript interaction before their core explanatory content becomes available.

Client-side JavaScript can enhance the checker, but the page purpose, primary answer, headings, supporting explanation, and internal links should be available to crawlers.

## 6. Structured data

Use JSON-LD when appropriate because it is generally easiest to implement and maintain.

### Homepage

Recommended entity markup:

- `WebSite` for site-name identity
- `Organization` only if the site actually represents an organization with truthful properties

Example template:

```json
{
  "@context": "https://schema.org",
  "@type": "WebSite",
  "name": "Can I Share This?",
  "url": "https://YOUR-PRODUCTION-DOMAIN/"
}
```

### SEO landing pages

Use `BreadcrumbList` where the visible navigation supports the hierarchy.

Example conceptual hierarchy:

Home > Google Drive > Google Drive Link Checker

Do not add structured-data properties that are not visible or verifiable on the page.

### FAQ content

Keep the FAQ sections visible because they help users and semantic coverage. Do not build the implementation around Google FAQ rich results. The FAQ rich-result feature was removed from Google Search in 2026.

## 7. Internal linking

Homepage should provide crawlable HTML links to the two main service hubs:

- `/google-drive-link-checker`
- `/dropbox-link-checker`

Google Drive hub should link to all Google Drive supporting pages.
Dropbox hub should link to all Dropbox supporting pages.
The comparison page should bridge both clusters.

Use descriptive anchors such as:

- Check Google Drive link access
- Diagnose a Dropbox link that is not working
- Check whether a Dropbox link may be expired

Avoid repeated generic anchors such as `click here`.

## 8. Prevent index bloat

Do not create one page for every tiny keyword permutation.

Reject or consolidate pages when:

- search intent is materially identical to an existing page
- the page would reuse mostly identical copy
- the page exists only to capture a keyword variant
- the page cannot provide additional product-specific evidence or utility

This is especially important for a tool site because scaled low-value landing pages can become a quality liability.

## 9. GEO / generative-search implementation

For Google Search's generative AI features, foundational SEO remains the underlying requirement. Do not implement pseudo-GEO hacks that add no user value.

Priorities:

1. Clear technical crawlability and canonicalization.
2. Unique, useful, non-commodity content.
3. Direct answer near the beginning of each landing page.
4. Product-specific evidence: real verdict examples, methodology, limitations, and screenshots where useful.
5. Accurate visible structured data only.
6. Strong page experience on mobile and desktop.
7. Search Console monitoring, including Generative AI reports when available to the property.

Do not create `llms.txt` merely as a Google Search optimization tactic. Google's 2026 guidance explicitly says unnecessary AI text files such as `llms.txt` are not required for its generative Search features.

## 10. Product-specific trust signals to add later

The strongest content moat for Can I Share This? will come from evidence generated by the product itself rather than generic SEO prose.

Recommended additions after the checker code is in the repo:

- anonymized real verdict examples
- examples of HTTP 200 + login-wall false positives
- Drive-specific permission-state examples
- Dropbox disabled/expired-link examples
- explanation of what is checked without browser cookies
- explicit confidence/uncertainty explanation
- clear privacy statement covering what is and is not stored
- methodology/update date

## 11. Performance guardrails

SEO pages must not materially degrade checker speed.

- Avoid large client-side libraries for static explanatory content.
- Server-render or statically render landing-page copy where the framework permits it.
- Lazy-load non-critical imagery.
- Set image dimensions to avoid layout shift.
- Keep interactive checker code shared rather than duplicated in each route.

## 12. Deployment sequence

1. Push current production source into the repo.
2. Identify framework and actual route structure.
3. Implement route manifest on a new integration branch.
4. Add metadata/canonicals.
5. Add sitemap and robots handling.
6. Add visible breadcrumbs and valid BreadcrumbList markup.
7. Wire contextual internal links.
8. Run production build locally/CI.
9. Deploy preview only.
10. Verify all 10 URLs return 200 and render their unique content.
11. Verify checker functionality is unchanged.
12. Validate structured data.
13. Check canonical tags and robots directives from rendered HTML.
14. Merge only after preview passes.
15. Submit sitemap in Search Console.
